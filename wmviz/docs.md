# Noridoc: wmviz

Path: @/wmviz

### Overview

`wmviz` is the top-level package: a Typer CLI ([wmviz/cli.py](wmviz/cli.py)) that lets a user list, filter, and pick episodes recorded by the `wm` training repo, then either eyeball one with a no-Blender preview ([wmviz/preview.py](wmviz/preview.py)) or render it — a single episode, a labelled figure, a training-milestone timeline, or an aggregate heatmap — through the Blender scene/camera/overlay pipeline or a matplotlib fallback. The actual trace parsing and selection logic lives one level down in [wmviz/trace/](wmviz/trace/docs.md); this folder is the user-facing layer built on top of it.

### How it fits into the larger codebase

`wmviz` is a standalone companion package to `wm` (see [@/docs.md](docs.md) at the repo root for the two-repo relationship and rationale). Within this repo, `wmviz/cli.py` is the single entry point registered as the `wmviz` console script (`[project.scripts]` in [pyproject.toml](pyproject.toml)); `wmviz/preview.py` is only ever imported by the CLI's `show` command, not used standalone. Both depend on [wmviz/trace/](wmviz/trace/docs.md) for `Index`, `Episode`, `Layout`, `find_runs`, `parse_ref`, and the filter/sort/pick functions. [tests/](tests/docs.md) exercises this layer end-to-end via Typer's `CliRunner`.

The Blender layer (needs the `blender` extra, i.e. `bpy`, Python 3.11 only) is built up in stages: [wmviz/scene/](wmviz/scene) turns a `Layout` into Blender objects, [wmviz/animate.py](wmviz/animate.py) keyframes them from an `Episode`'s arrays, [wmviz/cameras.py](wmviz/cameras.py) adds a camera preset, [wmviz/overlays.py](wmviz/overlays.py) adds the optional trail and visit heatmap, and [wmviz/render.py](wmviz/render.py) strings these together (`build`) and renders frames to PNG/MP4 for the `render`/`figure`/`timeline`/`heatmap` CLI commands. Everything bpy-free lives alongside it and doubles as the no-Blender path: [wmviz/aggregate.py](wmviz/aggregate.py) computes the per-cell visit counts and milestone/layout-grouping logic the aggregate commands consume, [wmviz/mpl.py](wmviz/mpl.py) draws the same stills with matplotlib (the `--backend mpl` path, and what `preview.py` reuses), and [wmviz/compose.py](wmviz/compose.py) (PIL) does all post-render compositing — stacking cameras, dream picture-in-picture/split, HUD, labelled strips/grids — for both backends. Nothing in `cli.py`, `preview.py`, `mpl.py`, `compose.py` or `aggregate.py` imports `bpy`; `render.py` imports the Blender modules lazily inside functions so `RenderConfig` and the compositing helpers stay importable without it, and `cli.py` picks a backend (`_backend`) by probing whether `bpy` imports before falling back to `mpl`.

### Core Implementation

**CLI ([wmviz/cli.py](wmviz/cli.py))** is a Typer `app` with a module-level `State` singleton (`state.logs`, default `Path("logs")`) set by the `--logs` option or `WMVIZ_LOGS` env var in the `@app.callback()`. Selection commands:
- `runs` — lists run directories under `--logs` that contain `trace/index.csv` (via `find_runs`), with env id and exploration method read from each run's *last* episode's `meta`.
- `list` — loads one run's `Index`, applies the shared `Filters` (phase/actor/after-step/before-step/success/min-cells/layout), sorts via `sort_rows`, and renders a Rich table capped at `--limit` (default 50), printing a "… N more" hint if truncated.
- `pick` — same filters, but resolves exactly one episode via one selector flag (`--best-return`, `--most-cells`, `--first-success`, `--first-door`, `--first-key`, `--at-step N`, `--latest`) and prints only its `<run>/ep000NNN` ref to stdout, so it composes in shell substitution (e.g. `wmviz show $(wmviz pick run --best-return)`). Passing zero or more than one selector flag fails with exit code 2.
- `show` — resolves one episode ref via `resolve_episode` (which calls `parse_ref` → `Index.load` → `Index.by_id` → `Episode.load`), prints its metadata/stats line and an ASCII map (`preview.ascii_map`), and optionally writes a PNG (`preview.save_png`) if `--png PATH` is given.

Render commands share `_target(target, filters, ...)`: `TARGET` is either `<run>/ep000123` directly or a run name plus exactly one selector flag (the same seven as `pick`), so every render command accepts either form.
- `render` — one episode as a Blender animation or `--still STEP` frame; `_render_options` validates arguments (resolution parity, camera list, `--no-render` needing `--save-blend`) before `_need_bpy()` is even checked, so bad flags fail fast without Blender installed. `--camera` defaults to `fpv` for dream episodes, `topdown` otherwise.
- `figure` — a still of one episode (`--keyframes auto|<steps>` turns it into a labelled strip via `mpl.keyframe_steps`/`compose.strip`), on the Blender or `mpl` backend (`_backend`: explicit `--backend`, else Blender if `bpy` imports, else `mpl` with a printed notice).
- `timeline` — the seed-fixed episode nearest each `--milestones` step (`aggregate.nearest_to_milestones`) as a labelled strip, or with `--video` a synced tiled mp4 built from each episode's per-frame `render.frames_composited` iterator via `_hold_last` (freezes a shorter animation on its last frame) and `compose.grid`.
- `heatmap` — accumulated visit counts (`aggregate.accumulate`) of one layout as a still, `--animate` for the floor filling in episode by episode (`render.render_heatmap_frames`, Blender only), `--compare RUN2` for a second run's heatmap tiled alongside (`compose.hstack`). Layout mixing across episodes is refused (`aggregate.same_layout`) unless `--force`.

Errors funnel through `_fail(msg, code=1)`, which prints `error: <msg>` in red and raises `typer.Exit(code)`; validation errors (bad selector counts, bad `--res`/`--sort`/`--keyframes`/`--milestones`) use exit code 2, everything else — including layout mismatches (`_same_layout_or_fail`) — exit code 1.

**Preview ([wmviz/preview.py](wmviz/preview.py))** has two independent functions, both no-Blender:
- `ascii_map(ep)` — builds a `Counter` of agent-visit counts per cell from `ep.agent_pos`, then renders the layout as a grid of characters: `#` wall, `D` door, `K` key, `G` goal, `~` lava, `.`/digit/`*` for unvisited/visited-N-times/visited-10+-times floor, with `S` (start) and `E` (end, overrides any other marker including `G`) overlaid last.
- `save_png(ep, out, cell_px=32)` — renders the same layout plus the agent's path via [wmviz/mpl.py](wmviz/mpl.py)'s `new_axes`/`draw_layout`/`draw_trail` and saves it to `out`. Matplotlib is imported lazily (inside `mpl._plt()`); if unavailable it raises `RuntimeError` telling the user to `uv sync --extra figures` rather than failing at module import time.

**mpl backend ([wmviz/mpl.py](wmviz/mpl.py))**: the no-bpy drawing code shared by `preview.py` and the `figure`/`heatmap --backend mpl` paths. `draw_layout` (walls/doors/goals/lava as colored rectangles, keys as markers), `draw_heatmap` (per-cell `magma` rectangles from a counts array), `draw_trail` (the agent's path as a `viridis`-colored `LineCollection`, start as a white circle) and `draw_agent` (a black square with a direction arrow) compose onto one `matplotlib` axes from `new_axes`; `figure_image`/`heatmap_image` wrap these into a finished frame via `fig_to_array`. `COLOR_RGB` here is the canonical MiniGrid color palette (`red`/`green`/`blue`/`purple`/`yellow`/`grey`); `preview.py` re-exports it and `scene/base.py` imports it from here so the ASCII/mpl/Blender paths never disagree on door/key colors.

**Render compositing ([wmviz/render.py](wmviz/render.py))**: every output frame goes through `compose_frame(images, ep, row, t, cfg)` — the per-camera PNGs are stacked side by side, then, for dream episodes only, the recorded observation and the world model's view of state `t` are composited in, and the HUD is drawn last so it stays on top. `dream_panels(ep, t)` resolves what the model view is: the posterior reconstruction (`recon_frames[t]`) while `t < dream_start`, the imagined frame (`dream_frames[t - dream_start]`) from then on, or `None` past the stored frames — and reports whether the model is dreaming yet. `RenderConfig.dream_layout` picks the composition: `pip` (default) stacks labelled "real obs" and "recon"/"dream" insets in the top-right corner, `split` puts the model view beside the rendered scene; in both, the inset border / divider is white while the model still tracks reality and black once it dreams, so the transition is visible without reading the HUD. Non-dream episodes pass through untouched. The `render` command defaults `--camera` to `fpv` for dream episodes (the imagined frames are first-person, so the Blender view should be too) and `topdown` otherwise; an explicit `--camera` always wins.

**Cameras ([wmviz/cameras.py](wmviz/cameras.py))**: `add_camera(preset, layout, ep, cfg)` creates `Cam_<preset>`, makes it `scene.camera` and returns it. `topdown` (orthographic, straight down over the layout centre) and `iso` (perspective, looking at the centre from a diagonal) are static and accept `ep=None`; `follow`, `fpv` and `orbit` are keyframed at `step_frame(t)` for every state and raise `ValueError` without an episode. `fpv` sits at eye height in the agent's cell with the agent's yaw and follows `cfg.discrete`; `follow` trails 2.5 cells behind and above the agent through an EMA-smoothed, eased path; `orbit` does one linear 360° sweep around the layout over the episode. `look_at(obj, target)` points an object's -Z axis at a target and keeps the resulting Euler continuous with the object's previous one, so keyframed cameras never wrap through ±π and spin the long way round.

**Overlays ([wmviz/overlays.py](wmviz/overlays.py))** never touch materials: both effects drive `Object.color`, which the scene builder's materials read through an Object Info node. `add_trail` adds one thin cylinder per step in which the agent changed cell (turn-only steps produce nothing), into a `Trail` collection registered in `SceneObjects.collections`; each segment is coloured by `time_color(t / T)` (a viridis-like ramp) and keyframed hidden until `step_frame(t)` via `keyframe_hidden`, so the trail grows with the animation. `add_heatmap` keyframes every floor tile's `Object.color` with `heat_color(cumulative_count / final_peak)` (black → red → yellow) at each step the tile's count changes, with CONSTANT interpolation so a tile jumps at the step boundary rather than fading in. `set_heatmap_static` sets the same colours once from a `(W, H)` counts array with no keyframes, for the aggregate `heatmap` command. `build()` in `render.py` applies them between `animate` and the cameras when `RenderConfig.trail` / `.heatmap` are set, and both flags are part of the frames-directory fingerprint so a resumed render never mixes overlay and non-overlay frames.

### Things to Know

- `Filters`/selector construction is duplicated as explicit Typer `Option` objects (`_PHASE`, `_ACTOR`, etc.) at module level in `cli.py` and reused across `list_cmd` and `pick_cmd`, because Typer has no built-in option-group mechanism — the comment in the code calls this out directly.
- `show`'s stats line always prints `key@`/`door@`/`goal@`/`rooms=` fields even when they're `None` (rendered as empty string by `_fmt`), since not every phase records those milestones.
- Camera conventions match the scene builder: cell `(x, y)` sits at `(x + 0.5, -(y + 0.5))`, `agent_dir` 0..3 maps to yaw 0°, -90°, 180°, 90°, and the fpv camera's Euler is `(π/2, 0, yaw − π/2)` so yaw 0 looks along +X.
- Door cells have no floor tile, so visits to a door cell count towards the heatmap's peak but are never drawn; and an episode in which the agent only turns in place yields a valid, empty trail.
- The pip inset stack for a dream episode (two insets at a quarter of the frame height, each with a 3 px border and an 18 px label) needs roughly 120 px of frame height; `compose.pip` raises `ValueError` when the block does not fit. Real renders (preview 540 px, default 1080 px) are far above that — it only matters for tiny synthetic frames in tests.
- `COLOR_RGB` (canonical in `mpl.py`) is a small fixed palette matching the `IDX_TO_COLOR` values decoded in [wmviz/trace/reader.py](wmviz/trace/reader.py) — the two must stay in sync for door/key colors to render correctly.
